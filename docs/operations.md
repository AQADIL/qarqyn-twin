# Эксплуатация QARQYN

Приложение работает одним процессом Node.js с локальной SQLite. Сервер и браузер используют один origin. Это описание реализованных механизмов; отказоустойчивый кластер, промышленная интеграция и внешний архив резервных копий здесь не настроены.

## Запуск и конфигурация

Требуется Node.js 22.13 или новее. Из корня репозитория:

```sh
npm ci
npm run setup
npm run build
npm start
```

`setup` создаёт локальный `.env` с отдельными случайными реквизитами и доступным портом. Существующий `.env` не перезаписывается. Не публикуйте его и не переносите тестовые реквизиты в публичный деплой. Конфигурация сервера задаётся через переменные окружения; `npm start` читает `.env`.

| Переменная | Назначение |
| --- | --- |
| `HOST`, `PORT` | Адрес и порт слушающего процесса. За обратным прокси предпочтителен интерфейс, недоступный напрямую клиентам. |
| `APP_ORIGIN` | Единственный разрешённый origin, включая протокол и порт. Production вне localhost требует HTTPS. |
| `DATABASE_PATH` | Путь к SQLite. Сохраните файл и связанные WAL/SHM в каталоге с правами только для серверной учётной записи. Для копирования работающей базы используйте backup, а не файловое копирование одного `.sqlite`. |
| `ADMIN_USERNAME`, `ADMIN_PASSWORD` | Учётная запись владельца; пароль 16–256 символов. Изменение реквизитов применяется при запуске и отзывает прежние сессии владельца. |
| `SESSION_HOURS` | Время жизни сессии, ограничено сервером диапазоном 1–24 часа. |
| `TRUST_PROXY` | Через запятую: конкретные доверенные IP, CIDR или категории Express `loopback`, `linklocal`, `uniquelocal`. Пустое значение отключает доверие. `true` и количество переходов запрещены. |
| `BACKUP_DIR` | Каталог резервных копий. Если не задан, используется `backups` рядом с файлом базы. |
| `AUDIT_RETENTION_DAYS` | Срок хранения записей аудита; `0` отключает удаление. |
| `CHAT_RETENTION_DAYS` | Срок хранения неактивных разговоров; `0` отключает удаление. Разговоры с выполняющимся запросом не удаляются. |
| `BACKUP_KEEP_COUNT` | Сколько новых резервных копий оставлять; `0` отключает удаление. |

Прокси должен передавать исходный Host и самостоятельно устанавливать корректный `X-Forwarded-For`, удаляя недоверенные значения клиента. Ограничьте прямой доступ к приложению и доверьте только адрес прокси. Одинаково важны корректные Host, Origin и cookie Secure: при HTTPS-origin браузер должен обращаться через HTTPS.

## Резервные копии и восстановление

Администратор создаёт копию в разделе «Управление → Копии данных». Используется `VACUUM INTO`: снимок согласован с транзакцией, проверяется `PRAGMA integrity_check` и только затем получает окончательное имя. Копия остаётся на сервере; перенос за пределы машины и расписание организует владелец инфраструктуры.

Для локальной командной строки существуют три операции:

```sh
node scripts/database.js backup --source PATH_TO_DATABASE --destination NEW_BACKUP_PATH
node scripts/database.js verify --source PATH_TO_BACKUP
node scripts/database.js restore --source PATH_TO_BACKUP --destination NEW_DATABASE_PATH
```

Аргументы `PATH_TO_DATABASE`, `PATH_TO_BACKUP`, `NEW_BACKUP_PATH`, `NEW_DATABASE_PATH` замените реальными путями; пути с пробелами заключите в кавычки. Команды никогда не перезаписывают существующий файл назначения. `restore` проверяет источник и создаёт новый SQLite-файл. Затем остановите приложение, измените `DATABASE_PATH` на новый путь и запустите сервер. Проверьте готовность, вход и историю данных до удаления прежней базы. Пароль владельца берётся из текущего окружения, поэтому восстановленный старый пароль не сохраняется против настроенной конфигурации.

Миграции применяются последовательно внутри транзакций и отмечаются в `schema_migrations`/`PRAGMA user_version`. Приложение отказывается открывать более новую поддерживаемой версию схемы. Архив версий наборов начинается с версии, существовавшей при установке механизма истории; утраченные старые версии он не воссоздаёт. Восстановление набора через интерфейс создаёт следующую версию, сохраняя предыдущие снимки.

## Хранение и аудит

Настройка срока не запускает фоновое удаление. Администратор явно применяет сроки в «Управление → Состояние». Удаление записей БД выполняется транзакционно; удаление резервных файлов имеет отдельные события запроса, успеха или отказа и итоговую запись. По умолчанию аудит, разговоры и резервные копии сохраняются. История стоимости ИИ не удаляется вместе с разговорами: иначе локальный бюджет ошибочно обнулился бы.

CRUD наборов, сценариев, задач и пользователей записывает аудит в той же транзакции. При отказе аудита изменение откатывается. Для обновлений и удалений требуется текущая версия. Сохранение сценария дополнительно требует `expectedDatasetVersion`; сервер сам пересчитывает результат и сохраняет версию источника.

## Мониторинг и доступ

- `GET /api/health/live` проверяет, что HTTP-процесс отвечает.
- `GET /api/health/ready` проверяет схему, возможность записи с откатом и наличие production-сборки. Возвращает `503` при недоступности. Проверка не изменяет пользовательские записи.
- `GET /api/operations` доступен администратору и показывает версию схемы, режим SQLite, готовность, сведения о runtime, копиях и резервах ИИ.
- HTTP-запросы и серверные ошибки журналируются JSON-строками с requestId. Пароли, содержимое запросов и ключи не пишутся в эти события. Сбор и ротацию stdout/stderr настраивает среда запуска.

Администратор создаёт редакторов и наблюдателей, меняет их роли и приостанавливает доступ. Изменение аккаунта отзывает его сессии. Владелец управляется только окружением сервера. Рабочие наборы принадлежат создателю и доступны администратору; приглашение пользователя само по себе не предоставляет ему чужой рабочий набор. Исходный набор доступен всем вошедшим пользователям. Чаты принадлежат пользователю и привязаны к набору.

## ИИ: история, остановка и стоимость

Без настроенного провайдера расчёты продолжают работать, отправка сообщений отключается. Модель, URL, ключ, тарифы, лимит бюджета, предел ответа и timeout задаются `AI_*` в `.env.example`. Это локальный учёт расходов по заданным тарифам, а не чтение баланса провайдера.

Чат хранит вопросы и проверенные ответы на сервере. SSE передаёт состояние обработки и финальный ответ после проверки структуры и ссылок. Кнопка остановки прерывает запрос к провайдеру; закрытие соединения делает то же самое. Остановка не гарантирует отмену списания у провайдера, поэтому неоднозначный расход остаётся зарезервированным. После перезапуска незавершённые сообщения помечаются прерванными, бюджет сохраняется.

Администратор сверяет незавершённые резервы в «Управление → Учёт ИИ», опираясь на подтверждение провайдера: «не списано» или фактическая сумма с примечанием. Активный запрос сверить нельзя. Повторная сверка одного резерва отклоняется. Для больших наборов полные агрегаты дополняются ограниченной выборкой последних строк; ограничение явно добавляется в ответ, а ссылки на непереданные строки отклоняются.

## Проверки

```sh
npm test
npm run build
npx playwright install --with-deps chromium firefox webkit
npm run test:e2e
```

E2E поднимает отдельный production-сервер для каждого браузера с временной БД, случайными логином, паролем и свободным портом. Реальный `.env` не читается, API ИИ отключён. Проверяются вход, темы, мобильное меню, рабочая копия, конфликт версий, история/восстановление, CRUD задач, сравнение наблюдений, отключённый помощник и управление аккаунтом. XLSX проверяется настоящим файлом через worker, валидацию сервера и сохранение отдельного набора. Сценарии проходят сохранение и сравнение со снимком, а недостаточные наблюдения должны показывать понятную ошибку. На мобильном экране отдельная проверка прокрутки перематывает настоящий видеофайл вперёд и назад. В CI эти проверки выполняются отдельно в Chromium, Firefox и WebKit. Это функциональные проверки; они не доказывают отсутствие всех уязвимостей или поведение при промышленной нагрузке.
