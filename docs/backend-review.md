# Проверки backend и расчётных моделей

Проверки воспроизводятся из репозитория. Результат конкретного коммита доступен в [CI](https://github.com/AQADIL/qarqyn-twin/actions/workflows/ci.yml).

```bash
npm test
npm run build
npm run test:e2e
```

Браузерные сценарии используют отдельную базу. Автоматические проверки ИИ задают ответы только внутри тестового процесса: проверяют контракт и ошибки, не вызывают платный API и не доказывают качество рассуждения провайдера.

## Существенные свойства реализации

- Плановые и неклассифицированные остановки не создают резерв. В мероприятиях одна запись учитывается один раз, восстановление ограничено её длительностью.
- Перед передачей в задачи требуются инженерное подтверждение, источник оценки, ответственный, срок, расходы и способ проверки. Уверенность инженера не умножает выпуск и не является измеренной вероятностью успеха.
- Изменение исходной версии блокирует передачу задач; интерфейс снимает подтверждения при загрузке старого плана. Повтор неизменённой версии возвращает уже созданные задачи.
- Событийная модель объединяет пересечения по станку и проверяет сохранение деталей. Неизвестные параметры вводятся явно; средний цикл из таблиц служит только ориентиром.
- Независимая проверка фиксирует метод до контрольного отрезка. Статус преимущества требует достаточной истории, улучшения MAE, устойчивости временных блоков и положительной нижней границы блочной перепроверки.
- Сохранённые инженерные расчёты содержат условия, результат, версию и хеш данных. Клиент не может подменить серверный результат при сохранении.
- Пропуски не становятся нулевым браком или простоем. Нулевой простой требует подтверждённого полного журнала за период.
- Пароли хешируются scrypt; API проверяет сессию, роль, владение, Origin и CSRF. Ошибки не возвращают серверный стек. CSV защищён от формульных префиксов.

## Границы доказательности

Пройденные тесты подтверждают проверенные свойства реализации. Они не являются промышленной валидацией, независимым аудитом всех уязвимостей или гарантией отсутствия ошибок.

Нужны реальные история и схема линии, проверенная интеграция, контрольный пилот, измеренные расходы и спрос. Событийная модель не описывает все технологические процессы, а прогноз не диагностирует конкретный отказ. Существующий ID в ответе ИИ подтверждает запись, но не истинность фразы. Для эксплуатации необходимы нагрузочные проверки, восстановление из копии, мониторинг и согласованная схема доступа.
