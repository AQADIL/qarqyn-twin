# Обратное планирование

Пользователь задаёт желаемый выпуск годных автомобилей и расчётный горизонт. Сервер находит минимальное необходимое восстановление времени каждого участка при неизменных скорости и качестве в существующей последовательной модели. OpenAI для расчёта не используется.

## API

`POST /api/plan-target`, JSON, авторизованная сессия, Origin и CSRF-токен. Расчёт доступен также гостю, только в наборах, которые ему доступны. Лимит: 30 запросов в минуту на IP; общий API-лимит также действует.

```json
{
  "datasetId": "allur",
  "hours": 8,
  "observationHours": 8,
  "targetGoodOutput": 109
}
```

`hours`: 1–744; `observationHours`: 1–24, по умолчанию 8; `targetGoodOutput`: больше нуля, не более 1 000 000. Неизвестные поля отклоняются. Отсутствующие наблюдения выпуска, времени или качества производственного участка дают 422. Неполное качество не заменяется нулевым браком.

Основные поля ответа:

| Поле                  | Значение                                                                                                                                                                          |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `achievable`          | Достижимость цели при доступных минутах и фиксированном качестве                                                                                                                  |
| `reasonCode`          | `already_met`, `achievable` или `beyond_capacity`                                                                                                                                 |
| `reason`              | Объяснение по-русски                                                                                                                                                              |
| `targetGoodOutput`    | Запрошенная цель                                                                                                                                                                  |
| `baseline`            | Базовый результат `{output, steps}`, с округлением лаборатории                                                                                                                    |
| `baselineGoodOutput`  | Базовый выпуск без округления для проверки достижимости                                                                                                                           |
| `maxGoodOutput`       | Верхняя граница выпуска при максимальном разрешённом восстановлении                                                                                                               |
| `shortfall`           | `max(0, targetGoodOutput − maxGoodOutput)`                                                                                                                                        |
| `totalRecoverMinutes` | Сумма восстановления в минутах на исходный период                                                                                                                                 |
| `input`               | Готовый `SimulationInput`, либо `null` для недостижимой цели                                                                                                                      |
| `result`              | Пересчитанный `SimulationResult`, либо `null`                                                                                                                                     |
| `interventions`       | Только участки с положительным восстановлением: `stageId`, `name`, `recoverMinutes`, `availableMinutes`, `excludedPlannedMinutes`, `sourceIds`                                    |
| `evidence`            | Все участки с наблюдаемым/доступным временем, выходом годных последующих операций, ограничениями выпуска и ID источников; `excludedSourceIds` перечисляет исключённое плановое ТО |
| `assumptions`         | Допущения, ограничения и объяснение минимальности                                                                                                                                 |
| `datasetVersion`      | Версия набора, по которой выполнен расчёт                                                                                                                                         |

Если цель уже достигается, `input.interventions` пуст; результат равен базе. Если цель недостижима, сервер не выдаёт заведомо неподходящий план. Успешный `input` сохраняется обычным `POST /api/scenarios` с `name`, `note` и актуальным `expectedDatasetVersion`, при наличии прав редактора. В `input` доля брака у вмешательств остаётся `null`, то есть используется историческое качество.

## Почему решение минимально

Пусть `vᵢ` — скорость участка, `H` — горизонт, `P` — длительность исходного периода в минутах, `Dᵢ` — средний наблюдаемый простой, `rᵢ` — восстановление времени, `qᵢ` — доля годных. Качество берётся из того же расчёта, что использует лаборатория сценариев.

Производственная ёмкость:

```text
Cᵢ(rᵢ) = vᵢ × H × max(0, 1 − (Dᵢ − rᵢ) / P)
Qᵢ = произведение qⱼ для j от i до последнего участка
Итоговый выпуск = minᵢ(Cᵢ(rᵢ) × Qᵢ)
```

Чтобы итог был не ниже положительной цели `T`, каждое независимое ограничение должно дать как минимум `T`. При ненулевых скорости и выходе годных отсюда следует:

```text
rᵢ ≥ Dᵢ − P + T × P / (vᵢ × H × Qᵢ)
rᵢ* = max(0, правая часть)
```

Если найденная компонента превышает разрешённые минуты, цель недостижима. Иначе вектор нижних границ достигает цели. Уменьшение любой его положительной компоненты нарушает соответствующее ограничение. Поэтому это покомпонентный минимум, в частности минимум суммы минут, при независимых ограничениях этой модели. Это не минимум денежной стоимости или расписания ремонтных бригад: таких данных нет. Для сравнений используется относительная численная погрешность `1e-9` от цели; число минут не округляется перед пересчётом сценария.

## Ограничения времени и обслуживания

Из доступного времени исключаются строки с явно указанной причиной «Плановое ТО», без учёта регистра и повторных пробелов. Это распознавание конкретного обозначения источника, а не классификатор остальных видов обслуживания. Другие причины остаются **условно доступными** для сравнения, и их устранимость должен подтвердить инженер. Лимит восстановления — минимум оставшегося наблюдаемого времени и 480 минут на исходный период, в соответствии с лабораторией.

Простои относятся к отдельным машинам; их сумма не доказывает длительность остановки участка и может включать пересекающиеся события. Плановое ТО не отменяется, команды оборудованию не отправляются. Единый `recoveryLimits` применяется также к лаборатории, сравнению сценариев и проверке предложений ИИ. Скорость, качество, период строки и независимость участков остаются допущениями. Фактический выпуск требует проверки на подробной истории предприятия.

## Проверяемый пример Allur

При `hours=8`, `observationHours=8` базовый результат составляет около **106,40256**, а предел при неизменном качестве и исключении планового ТО — **109,34186** расчётного автомобиля. Цель **109** достижима в модели; **110** — нет. Это расчёт из исходных строк, а не обещание фактического выпуска или измеренный эффект внедрения.

Автоматические проверки включают ручные двухступенчатые примеры, минимальность каждой компоненты, потери качества последующих операций, цель ниже базы, недостижимость, исключение планового ТО, лимит 480 минут, отсутствующие данные, валидацию запроса, доступ гостя и изоляцию чужих наборов.

## Частичная реализация и экономика

`POST /api/impact` использует тот же обратный план. Дополнительно принимает обязательный `expectedDatasetVersion`, `realizationPct` от 0 до 100, целое `periods` от 1 до 366 и необязательные неотрицательные `unitContribution` / `implementationCost`. Чужой набор недоступен; несовпадение версии возвращает `409`.

Доля реализации уменьшает найденные минуты восстановления, затем пересчитывается вся цепочка. Это не простое масштабирование итогового выпуска и не вероятность успешного внедрения. Для цели 109 при 50% реализации восстановление сварки составляет около 5,5231 минуты, результат — **107,7013** расчётной единицы за 8 часов. Цель 109 при этом ещё не достигнута.

Экономический расчёт использует дополнительный выпуск за выбранное число одинаковых периодов, маржинальный вклад дополнительной годной единицы и единовременные затраты пользователя. Пока суммы не введены, денежные показатели отсутствуют. При недостижимой цели положительная выгода не публикуется. Срок покрытия затрат является условным числом повторений расчётного горизонта; спрос, постоянство режима, налоги и регулярные новые затраты требуют отдельного обоснования.
