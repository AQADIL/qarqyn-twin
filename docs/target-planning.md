# Обратное планирование

Пользователь задаёт желаемый выпуск годных автомобилей и расчётный горизонт. Сервер находит минимальное необходимое восстановление времени каждого участка при неизменных скорости и качестве. Текущие версии: последовательная модель потока **v3**, обратное планирование **v2**, экономика **impact-v2**. OpenAI для этих расчётов не используется.

## API

`POST /api/plan-target`, JSON, авторизованная сессия, Origin и CSRF-токен. Расчёт доступен также гостю, только в наборах, которые ему доступны. Лимит: 30 запросов в минуту на IP; общий API-лимит также действует.

```json
{
  "datasetId": "allur",
  "hours": 8,
  "observationHours": 8,
  "targetGoodOutput": 109
}
```

`hours`: 1–744; `observationHours`: 1–24, по умолчанию 8; `targetGoodOutput`: больше нуля, не более 1 000 000. Необязательная `date` (`YYYY-MM-DD`) одинаково фильтрует производство, качество, события и подтверждения полноты. Неизвестные поля отклоняются. Отсутствующие или несопоставимые наблюдения дают `422`, а не искусственно полный расчёт.

Нужны одинаковые даты всех производственных участков, одна линия и запись на участок и дату, качество за каждую дату, одинаковый заданный режим. Если `periodHours` заполнен, он нужен во всех строках и должен совпадать с `observationHours`. `runtimeHours` не может превышать выбранный исходный период. Неполное качество не заменяется нулевым браком. Если простои полностью отсутствуют, требуется явное подтверждение полноты журнала `observationCoverage`; наличие отдельных событий без полной истории оставляет сценарий условным по зарегистрированной части потерь.

Основные поля ответа:

| Поле                  | Значение                                                                                                                                                                      |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `achievable`          | Достижимость цели при доступных минутах и фиксированном качестве                                                                                                              |
| `reasonCode`          | `already_met`, `achievable` или `beyond_capacity`                                                                                                                             |
| `reason`              | Объяснение по-русски                                                                                                                                                          |
| `targetGoodOutput`    | Запрошенная цель                                                                                                                                                              |
| `baseline`            | Базовый результат `{output, rawOutput, steps}`: `rawOutput` сохраняет полную точность, `output` округлён для вывода                                                           |
| `baselineGoodOutput`  | Базовый выпуск без округления для проверки достижимости                                                                                                                       |
| `maxGoodOutput`       | Верхняя граница выпуска при максимальном разрешённом восстановлении                                                                                                           |
| `shortfall`           | `max(0, targetGoodOutput − maxGoodOutput)`                                                                                                                                    |
| `totalRecoverMinutes` | Сумма восстановления в минутах на исходный период                                                                                                                             |
| `input`               | Готовый `SimulationInput`, либо `null` для недостижимой цели                                                                                                                  |
| `result`              | Пересчитанный `SimulationResult`, либо `null`                                                                                                                                 |
| `interventions`       | Только участки с положительным восстановлением: `stageId`, `name`, `recoverMinutes`, `availableMinutes`, `excludedPlannedMinutes`, `sourceIds`                                |
| `evidence`            | Участки, доступное время, выход годных следующих операций, ограничения и источники; `excludedSourceIds`, `unknownSourceIds`, `classificationEvidence` объясняют классификацию |
| `assumptions`         | Допущения, ограничения и объяснение минимальности                                                                                                                             |
| `datasetVersion`      | Версия набора, по которой выполнен расчёт                                                                                                                                     |

Если цель уже достигается, `input.interventions` пуст; результат равен базе. Если цель недостижима, сервер не выдаёт заведомо неподходящий план. Успешный `input` сохраняется обычным `POST /api/scenarios` с `name`, `note` и актуальным `expectedDatasetVersion`, при наличии прав редактора. В `input` доля брака у вмешательств остаётся `null`, то есть используется историческое качество.

## Почему решение минимально

Пусть `vᵢ` — скорость участка, `H` — горизонт, `P` — длительность исходного периода в минутах, `Dᵢ` — средний наблюдаемый простой, `rᵢ` — восстановление времени, `qᵢ` — доля годных. Качество берётся из того же расчёта, что использует лаборатория сценариев.

Производственная ёмкость:

```text
Cᵢ(rᵢ) = vᵢ × H × max(0, 1 − (Dᵢ − rᵢ) / P)
Qᵢ = произведение qⱼ для j от i до последнего участка
Итоговый выпуск = minᵢ(Cᵢ(rᵢ) × Qᵢ)
```

Чтобы итог был не ниже положительной цели `T`, каждое независимое ограничение должно дать как минимум `T`. При ненулевых скорости и выходе годных отсюда следует:

```text
rᵢ ≥ Dᵢ − P + T × P / (vᵢ × H × Qᵢ)
rᵢ* = max(0, правая часть)
```

Если найденная компонента превышает разрешённые минуты, цель недостижима. Иначе вектор нижних границ достигает цели. Уменьшение любой его положительной компоненты нарушает соответствующее ограничение. Поэтому это покомпонентный минимум, в частности минимум суммы минут, при независимых ограничениях этой модели. Это не минимум денежной стоимости или расписания ремонтных бригад: таких данных нет. Для сравнений используется относительная численная погрешность `1e-9` от цели; число минут не округляется перед пересчётом сценария.

## Ограничения времени и обслуживания

Явное поле `classification` принимает `planned`, `unplanned`, `unknown` и имеет приоритет над текстом причины. Для старых данных ограниченное правило распознаёт однозначные формулировки и показывает основание `legacy-label`. Остальные причины остаются неизвестными. Плановые и неизвестные события исключаются из восстановления; доступны только внеплановые минуты с инженерной проверкой устранимости. Лимит — минимум среднего зарегистрированного внепланового времени и 480 минут на исходный период.

В исходном Allur «Ошибка датчика» и «Обрыв цепи» распознаются как внеплановые, «Плановое ТО» защищено, а «Замена фильтра» остаётся неизвестной. На сварке из 27,5 минуты в среднем доступны 12,5; 15 минут ТО сохраняются. На окраске доступны 0 минут до явного уточнения классификации. Исходный JSON не дополняется выдуманными метаданными.

Простои относятся к отдельным машинам; их сумма не доказывает длительность остановки участка и может включать пересекающиеся события. Плановое ТО не отменяется, команды оборудованию не отправляются. Единый `recoveryLimits` применяется также к лаборатории, сравнению сценариев и проверке предложений ИИ. Скорость, качество, период строки и независимость участков остаются допущениями. Фактический выпуск требует проверки на подробной истории предприятия.

## Проверяемый пример Allur

При `hours=8`, `observationHours=8` на неизменном `data/allur.json`:

| Значение                                                 |  Результат без округления до сравнения |
| -------------------------------------------------------- | -------------------------------------: |
| Базовый поток                                            |                     106.39996632996635 |
| Предел при текущем качестве и разрешённом восстановлении |                     109.33919191919193 |
| Восстановление сварки для цели 109                       | 11.057477518758162 мин/исходный период |

Цель **109** достижима в модели; **110** — нет. В версии v3 доля брака вычисляется по исходным количествам без раннего округления. Это объясняет небольшое отличие от ранее сохранённых расчётов. Таблица не является обещанием фактического выпуска или измеренным эффектом внедрения.

Автоматические проверки включают ручные двухступенчатые примеры, минимальность каждой компоненты, потери качества последующих операций, цель ниже базы, недостижимость, исключение планового ТО, лимит 480 минут, отсутствующие данные, валидацию запроса, доступ гостя и изоляцию чужих наборов.

## Частичная реализация и экономика

`POST /api/impact` использует тот же обратный план. Дополнительно принимает обязательный `expectedDatasetVersion`, `realizationPct` от 0 до 100 и целое `periods` от 1 до 366. Чужой набор недоступен; несовпадение версии возвращает `409`.

| Денежный ввод                 | Значение                                                                                               |
| ----------------------------- | ------------------------------------------------------------------------------------------------------ |
| `unitContribution`            | Маржинальный вклад проданной дополнительной годной единицы; без значения денежный эффект неизвестен    |
| `implementationCost`          | Единовременные затраты; без значения денежный эффект неизвестен                                        |
| `recurringCostPerPeriod`      | Дополнительные регулярные затраты на расчётный период; по умолчанию 0                                  |
| `maxAdditionalSalesPerPeriod` | Предел дополнительных продаж за период; `null` означает условную продажу всего дополнительного выпуска |

Суммы неотрицательны, не больше `1e12`, с точностью до двух знаков; положительная сумма не меньше 0,01. Продажи ограничены диапазоном 0–1 000 000. Денежные значения обозначены в KZT; они не взяты из финансов Allur.

Доля реализации уменьшает найденные минуты восстановления, затем пересчитывается вся цепочка. Это не простое масштабирование итогового выпуска и не вероятность успешного внедрения. Для цели 109 при 50% реализации восстановление сварки составляет около **5,5287 минуты**, вывод результата — **107,7000** расчётной единицы за 8 часов. Цель 109 при этом ещё не достигнута.

Экономика разделяет произведённые и проданные дополнительные единицы. Доход начисляется только на продажи, ограниченные введённым спросом. Из него вычитаются разовые и все регулярные затраты выбранного горизонта. ROI равен чистому эффекту, делённому на эти затраты. При нулевых затратах ROI отсутствует; если вклад продаж за период не покрывает регулярные расходы, конечная окупаемость не заявляется. Пока необходимые суммы не введены или цель недостижима, денежный результат `null`.

Условный срок окупаемости повторяет один и тот же режим и спрос. Налоги, дисконтирование, стоимость запасов, изменение спроса и доказательство финансового эффекта требуют отдельной модели и реальных данных.

## После расчёта: сравнить фактические наблюдения

`POST /api/pilot` принимает `datasetId`, `expectedDatasetVersion`, `stageId`, `beforeDates` и `afterDates`. Непересекающиеся выбранные даты должны существовать в наборе и идти в порядке «до, затем после». Результат содержит измеренные агрегаты, нормированные показатели, источники, версии и причины несопоставимости.

Для сравнимой разницы нужны одинаковые линия, явно заданная длительность и режим. Отсутствие качества или полного журнала простоев делает соответствующую разницу неизвестной. Одна дата даёт только описательный факт. Функция не подтверждает причинность, не выводит статистическую значимость и не создаёт денежную экономию. На исходных двух датах Allur длительность и режим не заданы, поэтому она честно возвращает причины, требующие уточнения, вместо заявления об успешном пилоте.
